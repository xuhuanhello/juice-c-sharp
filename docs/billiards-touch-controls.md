# 台球的触屏操作方案

**票：** [#139](https://github.com/xuhuanhello/juice-c-sharp/issues/139)（prototype）
**地图：** [#113](https://github.com/xuhuanhello/juice-c-sharp/issues/113)
**这份文档是什么：** 一个**提案**，给 #139 拿去反驳或采纳的。它不是操作手册 —— 描述的东西还不存在。

> ## ⚠️ 现在按不动
>
> 回合状态机在 [#138](https://github.com/xuhuanhello/juice-c-sharp/issues/138) 落地并测过（36/36），但**运行时没有任何东西调 `Shoot()`** —— 全仓只有测试在调（11 处），`BilliardsBreakProbe._breakOnStart` 在场景里是 0。
>
> 所以现在把包打到真机上：两端能建房、进房、入座，日志会打出 `两人齐了，座位 0 开球`，然后 **卡在 Break 阶段每 60 秒超时换一次人，无限循环**。缺的不是状态机，是驱动它的这一层。

本文里的每个数字，要么是这一轮在 Editor 里实测的，要么来自 tracker 上一张已关闭的票。凡是推断，都标了「推断」。

## 1. 决定一切的那条约束

**实测（iPhone SE 3，667 × 375 pt 横屏）：一颗球在屏幕上只有 8.5 pt 宽。** Apple 的最小可点区域是 44 pt。

也就是说球大约是「手指能可靠命中的最小目标」的五分之一 —— **白球没法被直接摸、拖或者点**，一个指尖盖住它和周围四颗。

| 朝向 | 可见范围 | 台子放得下吗 | 球的屏幕尺寸 |
|---|---|---|---|
| 横屏 667 × 375 | 4.48 × 2.52 m | 放得下，还有余量 | 8.5 pt |
| 竖屏 375 × 667 | 1.42 × 2.52 m | **放不下 —— 半个台子在屏幕外** | 15.1 pt |

（算法：正交相机 `orthographicSize = 1.26` 定死纵向 2.52 m，横向 = 纵向 × 宽高比。）

于是后面所有设计都从这一条推出来：**瞄准必须是间接的。** 玩家不去点「球该去哪」，而是在任意位置拖动、按拖动的位移改瞄准。这也是薄擦唯一可行的做法 —— 一次薄擦要亚度级精度，而 4.7 寸屏上任何直接触摸方案都给不出。

> ### 动手前先修一行：锁横屏
>
> 当前 `defaultInterfaceOrientation = AutoRotation` 且四个朝向全部允许。竖屏起来就有半个台子看不见。**任何真机运行之前先锁成横屏。**

## 2. 手势：拖动瞄准，抬手出杆

一个连续手势带出一杆需要的两个量。

```
                        ┌─────────────────────── 2.84 m ───────────────────────┐
     ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓
     ▓  ▝▔▔▘              ▝▔▔▘                          ▝▔▔▘               ▓
     ▓                                                                      ▓   1.42 m
     ▓      ●┄┄┄┄┄┄┄┄ 手指拖动方向                                          ▓
     ▓       ╲                                                              ▓
     ▓        ○ 白球 ┅┅┅┅┅┅┅┅┅┅┅┅┅┅┅┅┅┅▶ 瞄准线 ┅┅┅┅┅┅▶ ◉ 目标球            ▓
     ▓                                                                      ▓
     ▓  ▝▔▔▘              ▝▔▔▘                          ▝▔▔▘               ▓
     ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓
        ↑ 六个袋口是台面上的真洞（#136），不是库边的缺口
```

1. **在台面任意位置按下。** 不是按在球上（它只有 8.5 pt）。落点即锚点，瞄准按相对锚点的位移读。
2. **朝目标的反方向拖。** 瞄准线从白球往相反方向延伸 —— 像把杆往后拉，拉的方向决定它指向哪。拖动方向给角度。
3. **拖动长度决定白球会滚多远。** 按同一屏幕比例画：往后拖 30 cm 的台面距离，球就滚 30 cm。见第 3 节 —— 这一段必须实测，不能猜。
4. **抬手出杆。** 把手指滑回锚点＝取消。一条 `Shoot(aimAt, power, cueSpot)` 走 Reliable 出去；**在抬手那一刻之前对手什么都看不到。**

**为什么对手看不到**：瞄准与摆球是**本地意图**，从不过网络 —— [#127](https://github.com/xuhuanhello/juice-c-sharp/issues/127) 与 [#132](https://github.com/xuhuanhello/juice-c-sharp/issues/132) 定的。抬手时出去的是五个 float（方向 x、方向 z、力度、摆球位 x、摆球位 z）。

### 瞄准读快照，不读屏幕

屏幕上那颗白球比权威位置滞后约两个 tick 的插值（TickRate 30 下 66 ms）。瞄准算式读 `State.BallPositions[0]`，所以算的是真实台面。这是 [#135](https://github.com/xuhuanhello/juice-c-sharp/issues/135) §4，也是「回合切换收到即允许瞄准、不等球在屏幕上停稳」的原因。

`BilliardsGame.Shoot` 已经照这条写好了（ballInHand 时用摆球位，否则读快照里的白球位）。

## 3. 力度：为什么线性滑条是错的控件

距离随力度的**平方**变化。这正是 [#137](https://github.com/xuhuanhello/juice-c-sharp/issues/137) 的实质 —— 原先的指数 drag 模型让距离 ∝ 力度，那个幂次是错的，而走位的全部内容就是力度到距离的映射。

**本轮实测**（空台、白球从开球点沿 +X 击出，十个不撞库的点拟合）：

> **d = 1.262 · p²** 米（自由滚）
> 反过来，UI 真正需要的那个式子：**p = √(d / 1.262)**
>
> 系数从 p = 0.5 起稳定到三位小数（1.262、1.262、1.263、1.262、1.262、1.261、1.262）。p = 0.3 / 0.4 略低（1.166 / 1.239），因为速度掉到一步的量级以下时会被直接停住。

两条后果直接落在控件设计上：

- **power 1.30 把白球从开球点送到对面库边** —— 那是台面全部的跑道，2.10 m。
- **上限 4.0 的自由滚是 20 m** —— 约九个半跑道。它是给开球的，不是给走位的。

所以一条 0 到 4.0 的线性滑条，会把**每一次走位都挤进它下面三分之一**，那里一个指头宽的行程横跨「做安全球」到「大力轰」。

因此选拖拽长度：**拖拽映射到距离，距离映射到力度。** 拖一个台面长，球滚一个台面长。没有要学的标定，非线性藏进算式里、玩家碰不到。

| 力度 | 自由滚 | 停下 | 是什么杆 |
|---:|---:|---:|---|
| 0.3 | 0.10 m | 1.1 s | 轻碰，不到两个球径 |
| 0.5 | 0.32 m | 1.9 s | 短安全球 |
| 0.7 | 0.62 m | 2.4 s | 半台开外进袋 |
| 1.0 | 1.26 m | 3.4 s | 大半个台面 |
| 1.2 | 1.82 m | — | 接近整条跑道 |
| 1.3 | 2.10 m | — | 刚好够到对面库边 |
| 4.0 | 20.0 m | 4.5 s | 开球：九条跑道、若干次撞库 |

### 开球要单独一个答案

按屏幕比例拖，上限大约在 power 1.5（台子在屏幕上就那么宽），而开球要 4.0。

**提案**：仍然一个手势，**让拖拽越过台面进入库边留白**，在那里比例**刻意断掉**并给一个「超量程」标记。开球一局一次，且它的力度不是走位选择 —— 这是唯一一处「手感不一致」是诚实而不是困惑的地方。

**备选**：一个专门的「开球」按钮，直接满力。

> **硬上限 4.0。** 4.5 及以上开球会触发 containment（球冲出台面再被夹回；#137 实测，且改动前同一力度也有）。host 侧本来就会 clamp —— **UI 不该给出一个 host 会拒绝的量程。**

## 4. 自由摆球

两条犯规（白球落袋、首碰不是自己组的球含空杆）都把台面交给对手并允许任意合法位摆球。

**两次点，而不是一个模式开关**：点一下放白球，然后照常瞄准。出杆前可以再拖它。

host **永不驳回**摆球位。非法位置吸附到最近合法位 —— [#132](https://github.com/xuhuanhello/juice-c-sharp/issues/132) 定的，而且和「越界夹回台内」是同一个函数。驳回要付一个协议往返加一个等它的 UI 状态。

> **三样东西让一个位置非法，第三样最容易忘**：出了台面矩形；与台上已有的球重叠；以及 **压在袋口上**。袋口是台面上的真洞，所以白球中心落在离袋口中心 **12.2 cm** 以内会直接掉下去 —— 这一杆在打之前就没了。禁放半径就是这个数（`PocketNotchHalf + 2 × BallRadius = 0.065 + 0.057`），**UI 该把它画出来**，而不是让玩家自己撞上。

对手看不到拖动过程。与瞄准同理：抬手之前都是意图。

## 5. 屏幕上要显示什么

形状照 `RoomPanel` / `ConnectionDiagnosticsHud`：**IMGUI，不建 Canvas 层级**。

下面每一项**都已经在 `BilliardsGame` 的公开面上**，不需要改状态机。

| 屏幕上 | 从哪读 | 备注 |
|---|---|---|
| 谁的回合 | `State.TurnSeat` | 与 `LocalSeat` 比 |
| 我是哪一组 | `LocalSeat` | 座位 0 = 实色 1–7，座位 1 = 花色 9–15 |
| 双方各剩几颗 | `State.Remaining(seat)` | 由掩码派生，**不存** |
| 阶段 | `State.Phase` | `Break` / `Aim` / `Simulate` / `GameOver` / `RematchPending` |
| 自由摆球 | `State.HasFlag(BallInHand)` | 打开摆球那一下点击 |
| 回合倒计时 | — | 60 s，host 计时；本地倒数即可 |
| 对手掉线了 | `State.HasFlag(AwaitingReconnect)` | 冻住输入、显示等待 |
| 重连倒计时 | `ReconnectSecondsRemaining` | 30 s，**本地跑** —— 见下 |
| 赢家 / 作废 | `State.Winner`、`Abandoned` 标志 | **两句不同的话** |
| rematch 同意 | `HostReady` / `ClientReady` 标志 | 两个位双方都看得见 |

### 倒计时刻意是本地的

host 只发**一次标志位**，秒数从不上线。一个每 tick 都变的数，代价会超过整条状态消息（一回合约 139 字节 —— 这个数**本身还没拆开验，见 #138 的决议**）。所以客户端在标志立起来那一刻自己起一个 30 秒的钟。

30 秒的沉默与「卡死了」不可区分 —— 那正是 [#134](https://github.com/xuhuanhello/juice-c-sharp/issues/134) 要这个数可见的理由。

### 两句必须分开的话

一局结束可能是**有人赢了**，也可能是**掉线的人没回来**。`Abandoned` 且没有赢家**不是输**。告诉一个玩家他输掉了一局其实作废了的球，比什么都不说更糟。

### 两条这一轮量出来的可读性问题

- **6 号球是绿的，台布也是绿的。** 它的配色 `(0.10, 0.55, 0.25)` 对台布 `(0.10, 0.42, 0.24)` —— 逐球投影采样时，十六颗里只有它读不出与台布的区别。球的美术怎么做，这一对都要分开。
- **中袋不吃直进球。** 从台面中央正对中袋打，球沿库边滑过袋口而不掉；角袋正常。不是本票要修的，但**任何瞄准辅助若指向中袋就是在骗人**。

## 6. 真机报告（本票的另一半）

截图不是证据，「我打了一局看着没问题」也不是。`CONTRIBUTING.md` 的那条是**机器能判的报告**。

而 iOS 上**没有日志文件可收** —— `Debug.Log` 进设备 console 就没了。仓库已定的那条路是写 `Application.persistentDataPath`、用 `devicectl` 抄下来（`docs/verification-mcp.md` §8b-iOS 第 4 步）。**台球现有的报告写在 `Application.dataPath/../Logs`，那在真机上是只读的 app bundle，写不进去且失败是静默的。**

| 字段 | 什么样才算合理 |
|---|---|
| `connectionPath` | `Direct` 或 `Relayed`，且与当时的网络摆法对得上 |
| `roundTripTime` + `tickRate` | RTT 是 tick 的整数倍（30/s 即 33 ms 一档） |
| 每 tick `peakUnreliable` | 与 248 B@30 / 228@60 同量级，且**越过 MTU 1282 的 tick 数为 0** |
| `peakBacklog` | 走真 TURN 时**不再恒为 0** —— 恒 0 说明压根没压出背压 |
| 每一杆 `settleSeconds` | 3～5 s。读到 **15.0 s 就是上限在兜底**，物理有问题 |
| 每一杆 `firstContact` | 除真空杆外**不能是 −1**；−1 说明碰撞回调没到 |
| `winner` / `Abandoned` | 有座位赢了，或这局作废 —— **明说，不靠推断** |
| 那次重连 | 座位号不变、分组不变、断连前后落袋掩码一致 |

## 7. 待定 —— 这份文档就是为了拿到这几个答案

| # | 问题 | 我的推荐 |
|---|---|---|
| Q1 | 拖动瞄准，还是点一个目标点？ | **拖动。** 8.5 pt 一颗球，点不出薄擦，而薄擦是这个游戏的大半。但点只有一个动作而拖有三个 —— 如果 demo 里瞄准精度其实不重要，点更省事 |
| Q2 | 力度由拖拽长度给，还是滑条？ | **拖拽长度，按比例。** 控件自解释：想让球滚多远就拖多远。滑条不上非线性根本不好用，而上了非线性玩家就是在标定而不是在打球 |
| Q3 | 开球怎么够到 4.0？ | **拖过台面进入库边留白**，比例可见地断掉。备选：一个满力「开球」按钮 —— 开球一局一次，力度不是需要纠结的选择 |
| Q4 | 精灵图，还是正交相机拍 3D 球体？ | 这半个问号**可能已被现状消掉**：场景现在就是正交相机 + URP/Lit 球体，本轮核过（零洋红、16 颗球逐个采样、15 颗对上各自配色）。推荐**保留现状**，力气花在球号与「把 6 号从台布里分出来」 |
| Q5 | 报告用什么形状？ | 先例写 NUnit 形状的 XML，而它**在自己的 `framework` 属性里写明「不是 Unity Test Framework」** —— 因为一份误报自己身份的报告，会告诉读者首选路线跑过了而它没跑。**打一局台球不是一套契约**，`total/passed/failed` 可能是错的框。推荐**结构化 JSON，一条 claim 一行带实测值**，不借用测试框架的词汇 |
